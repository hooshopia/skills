# بازسازی کد بدون تغییر رفتار

قانون اصلی: **رفتار بیرونی عوض نمی‌شه.** اگه لازمه رفتار هم تغییر کنه، اون یک کار جداست و باید جدا انجام و تست بشه.

## ۱. قبل از دست زدن

1. محدوده رو روشن کن: کدوم فایل یا تابع، و هدف چیه (خوانایی، حذف تکرار، شکستن یک فایل بزرگ، آماده‌سازی برای قابلیت بعدی).
2. تست‌های موجود رو اجرا کن. اگه کدی که می‌خوای عوض کنی تست نداره، **اول تست مشخصه‌نویسی (characterization test)** بنویس: تست‌هایی که رفتار فعلی رو، حتی اگه عجیبه، ثبت می‌کنن.
3. برنامهٔ قدم‌ها رو بنویس و به کاربر نشون بده.

## ۲. قدم‌های کوچک

هر قدم یکی از این‌هاست و بعد از هر قدم تست‌ها اجرا می‌شن:

- تغییر اسم به اسمی که کار رو توضیح می‌ده
- بیرون کشیدن تابع یا ماژول
- حذف کد مرده (بعد از اطمینان که جایی صدا زده نمی‌شه؛ با جست‌وجو چک کن)
- یکی کردن کدهای تکراری
- جایگزینی شرط‌های تودرتو با بازگشت زودهنگام
- جدا کردن منطق خالص از I/O

اگه تستی خراب شد، همون قدم رو برگردون و کوچک‌ترش کن. چند قدم خراب رو با هم درست نکن.

## ۳. پایان

- همهٔ تست‌ها، لینت و type-check رو اجرا کن.
- diff رو مرور کن و مطمئن شو هیچ تغییر رفتاری (متن خطا، ترتیب خروجی، مقدار پیش‌فرض) ناخواسته جا نیفتاده.
- گزارش بده: چه چیزی بهتر شد، و چیزهایی که دیدی ولی عمداً دست نزدی.

## نکن

- بازسازی و قابلیت تازه رو در یک commit قاطی نکن.
- API عمومی (اسم تابع‌های export‌شده، مسیرهای HTTP، ستون‌های دیتابیس) رو بدون هماهنگی عوض نکن.
