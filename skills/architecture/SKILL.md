# معماری: فهمیدن و طراحی

دو حالت داره. از درخواست کاربر بفهم کدوم لازمه.

## حالت ۱: نقشهٔ کد موجود

1. نقطه‌های ورود رو پیدا کن: `main`، روترها، handlerها، کارهای زمان‌بندی‌شده، CLI.
2. ماژول‌های اصلی و وظیفهٔ هر کدوم رو در یک خط بنویس.
3. وابستگی‌ها رو دنبال کن: چه کسی چه کسی رو صدا می‌زنه، داده کجا ذخیره می‌شه، سرویس‌های بیرونی کدوم‌اند.
4. یک درخواست واقعی رو از ورود تا پاسخ دنبال کن و مسیرش رو بنویس.
5. خروجی: یک نمودار ساده (Mermaid یا فهرست تودرتو)، جدول ماژول‌ها، و ۳ تا ۵ نکتهٔ مهم (جاهای شکننده، تکرار، مرزهای نامشخص). فقط چیزی رو بنویس که در کد دیدی.

## حالت ۲: طراحی یک تغییر

1. نیازها و محدودیت‌ها رو روشن کن: بار، حجم داده، تیم، زمان، چیزهایی که نباید بشکنن.
2. **حداقل دو گزینه** پیشنهاد بده. برای هر کدام: شکل کلی، تغییرات لازم، مزایا، معایب، ریسک، هزینهٔ برگشت.
3. یکی رو با دلیل پیشنهاد کن. ساده‌ترین گزینه‌ای که نیاز رو برآورده می‌کنه معمولاً بهترینه.
4. اگه کاربر تأیید کرد، یک یادداشت تصمیم (ADR) بنویس:

```markdown
# ADR-NNN: <عنوان تصمیم>
وضعیت: پیشنهادی | پذیرفته‌شده
## زمینه
## تصمیم
## گزینه‌های دیگر و چرا نه
## پیامدها
```

در `docs/adr/` (یا هر جایی که پروژه این یادداشت‌ها رو نگه می‌داره) ذخیره کن.

## قواعد

- الگو برای الگو نیار. لایهٔ تازه، microservice یا event bus فقط وقتی که مشکل واقعی‌ای رو حل کنه.
- همیشه بگو تصمیم بعداً چقدر راحت عوض می‌شه.
