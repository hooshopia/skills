# بازبینی کد

## چی رو بازبینی کنی

- اگه کاربر فایل یا commit مشخصی نگفته: تغییرات commit‌نشده (`git diff` و `git diff --staged`)، و اگه نبود، تفاوت شاخهٔ فعلی با شاخهٔ اصلی (`git diff main...HEAD`).
- فقط diff رو نخون؛ اطراف هر تغییر رو هم بخون تا بفهمی کد در چه زمینه‌ای اجرا می‌شه.

## به ترتیب اهمیت بررسی کن

1. **درستی:** منطق اشتباه، حالت‌های لبه (خالی، null، صفر، خیلی بزرگ)، خطاهایی که بی‌صدا قورت داده می‌شن، شرط‌های برعکس.
2. **امنیت:** ورودی کاربر بدون اعتبارسنجی، SQL/command injection، XSS، راز در کد، دسترسی بدون مجوز، داده‌ی حساس در لاگ.
3. **داده و همزمانی:** مهاجرت‌های خطرناک، تراکنش ناقص، race condition (اگه جدیه، `race-check`).
4. **کارایی:** کوئری داخل حلقه (N+1)، کار سنگین در مسیر داغ، حافظهٔ بی‌حد.
5. **تست:** رفتار تازه تست داره؟ تست‌ها واقعاً چیزی رو چک می‌کنن؟
6. **خوانایی:** اسم‌های گمراه‌کننده، تابع‌های خیلی بلند، تکرار، کامنت‌های قدیمی.

سبک کدی که لینتر می‌گیره رو گزارش نکن.

## شکل گزارش

برای هر مورد:

```
[شدت] فایل:خط — مشکل در یک جمله
چرا مهمه: سناریوی مشخصی که خراب می‌شه
پیشنهاد: تغییر مشخص (در صورت لزوم با تکه‌کد)
```

شدت‌ها: **بحرانی** (باید قبل از merge درست بشه) · **مهم** · **پیشنهاد**.

آخر گزارش یک جمع‌بندی دوخطی بده: آمادهٔ merge هست یا نه، و مهم‌ترین کاری که باید بشه.

## قواعد

- فقط چیزی رو گزارش کن که بتونی سناریوی خرابیش رو توضیح بدی. حدس رو با «احتمالاً» مشخص کن.
- کد رو خودت تغییر نده مگر کاربر بخواد.
- اگه چیز خوبی دیدی که الگوی درستیه، یک خط بگو؛ بیشتر نه.
