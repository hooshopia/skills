# از ایده به مشخصات (Spec)

خروجی این اسکیل یک فایل `SPEC.md` (یا اسمی که کاربر بگه) در ریشهٔ پروژه یا پوشهٔ `docs/` است که یک ایجنت یا برنامه‌نویس بتونه بدون سؤال اضافه پیاده‌اش کنه.

## قبل از نوشتن

1. ورودی رو بخون: خلاصهٔ `grill-me`، گفت‌وگو، issue یا توضیح کاربر.
2. کد فعلی رو در حد لازم بررسی کن: ساختار پوشه‌ها، الگوهای موجود، مدل داده و APIهایی که تغییر می‌کنن. spec باید با کد واقعی جور باشه.
3. اگه چیزی حیاتی مبهمه (نه جزئیات)، حداکثر ۳ سؤال بپرس. بقیه رو در «سؤال‌های باز» بنویس.

## ساختار SPEC.md

```markdown
# <اسم قابلیت>

## هدف
یک پاراگراف: چه مسئله‌ای، برای چه کسی.

## خارج از محدوده
- چیزهایی که عمداً انجام نمی‌دیم.

## رفتار مورد انتظار
داستان‌های کاربر یا سناریوها، هر کدام با معیار پذیرش قابل‌تست:
- [ ] وقتی …، اگر …، آنگاه …

## طراحی فنی
- فایل‌ها و ماژول‌هایی که تغییر می‌کنن یا اضافه می‌شن
- مدل داده / مهاجرت دیتابیس
- API یا رابط‌ها (ورودی، خروجی، خطاها)
- حالت‌های لبه و خطا

## تست‌ها
چه چیزی با چه نوع تستی پوشش داده می‌شه.

## تسک‌ها
1. تسک کوچک و مستقل، با معیار «تمام شد»
2. …

## سؤال‌های باز
```

## قواعد

- معیارهای پذیرش باید **قابل‌تست** باشن. «سریع باشه» نه؛ «صفحه با ۱۰۰۰ ردیف زیر ۲۰۰ میلی‌ثانیه رندر بشه» بله.
- تسک‌ها رو طوری بشکن که هر کدام در یک commit جا بشن و بعدش تست‌ها سبز بمونن.
- چیزی رو که در ورودی نبوده، به‌عنوان تصمیم قطعی ننویس؛ یا بپرس یا در «سؤال‌های باز» بذار.
- بعد از نوشتن، خلاصهٔ کوتاه بده و پیشنهاد کن با `implement` از تسک ۱ شروع کنی.
